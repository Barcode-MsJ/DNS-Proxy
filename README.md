# DNS Proxy هوشمند — فاز اول شبکه‌های کامپیوتری

پیاده‌سازی Python برای پروژه فاز اول: مسدودسازی دامنه‌های تبلیغاتی، هدایت دامنه‌های فهرست تحریم، ارتباط UDP با Upstream شبیه‌سازی‌شده و کش محلی TTLدار. قابلیت‌های امتیازی B1 تا B6 نیز پیاده‌سازی شده‌اند. رابط وب یک افزونه مستقل است و موتور اصلی پروژه را جایگزین نمی‌کند.

## ۱) پیش‌نیازها

- Python 3.10 یا جدیدتر
- برای قابلیت B6 فقط: `dnspython`
- برای اجرای تست‌ها: `pytest`

نصب وابستگی‌ها در ویندوز:

```powershell
py -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
```

رابط وب از HTTP server استاندارد Python استفاده می‌کند و برای آن نیازی به Flask یا بسته وب جداگانه نیست. این انتخاب باعث می‌شود رابط وب بدون نصب چارچوب اضافی نیز قابل اجرا و تست باشد.

## ۲) اجرای نسخه اصلی CLI

ابتدا در ترمینال اول شبیه‌ساز Upstream را اجرا کنید:

```powershell
python upstream_mock.py
```

سپس در ترمینال دوم:

```powershell
python main.py
```

برنامه پیام `DNS Proxy ready.` را نمایش می‌دهد. نام دامنه را وارد کنید. برای خروج `exit` را وارد کنید.

دستورات امتیازی کنسول:

- `stats` — آمار درخواست‌ها (B1)
- `reload` — بارگذاری مجدد دو فهرست (B2)
- `cache` — نمایش ورودی‌های معتبر کش و TTL باقی‌مانده (B3)
- `exit` — خروج

## ۳) اجرای رابط وب

برای اجرای مستقل وب، ابتدا Upstream mock را اجرا کنید و سپس:

```powershell
python web/app.py
```

مرورگر را در این نشانی باز کنید:

```text
http://127.0.0.1:5000
```

داشبورد شامل استعلام دامنه، آمار، وضعیت Upstream، فهرست‌ها، کش و گزارش درخواست‌ها است. سرور وب به‌صورت پیش‌فرض فقط روی `127.0.0.1` گوش می‌دهد و از شبکه بیرونی قابل دسترسی نیست.

## ۴) اجرای هم‌زمان CLI و Web با یک موتور مشترک

اگر می‌خواهید CLI و وب دقیقاً یک نمونه از موتور، کش و آمار را به اشتراک بگذارند، Upstream mock را اجرا کنید و سپس:

```powershell
python run_both.py
```

در این حالت CLI در همان ترمینال فعال است و رابط وب نیز در `http://127.0.0.1:5000` در دسترس خواهد بود. در صورت اجرای مستقل `main.py` و `web/app.py` به‌عنوان دو پردازش جدا، هر پردازش نمونه مستقل خود از کش و آمار را خواهد داشت.

## ۵) تنظیمات

تمام تنظیمات اصلی از `config.txt` خوانده می‌شوند؛ IP، پورت و مسیر فهرست‌ها در کد هاردکد نشده‌اند. کلیدهای ضروری:

| کلید | توضیح |
|---|---|
| `upstream_ip` | IPv4 شبیه‌ساز یا DNS عمومی |
| `upstream_port` | پورت UDP Upstream |
| `sinkhole_ip` | IP پاسخ دامنه تبلیغاتی |
| `proxy_ip` | IP پاسخ دامنه تحریمی |
| `ad_list_file` | مسیر فایل فهرست تبلیغات |
| `sanction_list_file` | مسیر فایل فهرست تحریم |

کلیدهای دارای مقدار پیش‌فرض: `upstream_timeout_sec=2`، `local_ttl=60` و `cache_enabled=true`.

کلیدهای اختیاری امتیازی:

- `cache_max_entries=256` — سقف کش و سیاست حذف FIFO (B5). برای آزمون ظرفیت می‌توانید آن را `2` قرار دهید.
- `real_dns_enabled=false` — در حالت `true`، B6 فعال می‌شود. در این حالت باید `upstream_ip` برابر `8.8.8.8` یا `1.1.1.1` و `upstream_port=53` باشد.

برای فعال‌کردن DNS واقعی، ابتدا Upstream mock را متوقف کنید و این سه مقدار را در `config.txt` تنظیم کنید:

```ini
upstream_ip=8.8.8.8
upstream_port=53
real_dns_enabled=true
```

یا از `1.1.1.1` استفاده کنید. پاسخ واقعی فقط در صورت دسترسی شبکه به UDP/53 دریافت می‌شود. اگر اینترنت یا دسترسی UDP/53 وجود نداشته باشد، پاسخ `SERVER_ERROR` خواهد بود؛ برنامه متوقف نمی‌شود. در محیط اجرای فعلی، درخواست زنده به هر دو Resolver عمومی به Timeout خورد؛ بنابراین تست زنده موفق ادعا نمی‌شود. مقدار پیش‌فرض `real_dns_enabled=false` است تا تست‌های استاندارد T1 تا T13 همواره با Upstream محلی و تکرارپذیر اجرا شوند.

اگر فایل پیکربندی، کلید ضروری یا فایل فهرست لازم وجود نداشته باشد یا مقدار پیکربندی نامعتبر باشد، برنامه با پیام `Config error: ...` متوقف می‌شود. خطوط خالی و توضیحات `#` در فایل‌ها نادیده گرفته می‌شوند. خطوط نامعتبر در فهرست‌ها با Warning گزارش و رد می‌شوند.

## ۶) منطق تصمیم‌گیری و پروتکل

ترتیب تصمیم‌گیری دقیقاً مطابق سند است:

1. اعتبارسنجی ورودی
2. نرمال‌سازی (حروف کوچک و حذف یک نقطه انتهایی)
3. فهرست تبلیغاتی (اولویت اول)
4. فهرست تحریم
5. کش معتبر
6. Upstream

تطبیق فهرست فقط برای دامنه دقیق یا زیر‌دامنه با مرز نقطه انجام می‌شود؛ برای مثال `a.example.com` با `example.com` تطبیق دارد اما `notexample.com` ندارد. علامت `*` پشتیبانی نمی‌شود.

در حالت اجباری، Proxy یک UDP datagram با متن `QUERY <domain>` ارسال می‌کند. پاسخ‌های مجاز شبیه‌ساز `OK <IPv4> <ttl>` و `NOT_FOUND` هستند. فقط یک تلاش انجام می‌شود و Timeout/پاسخ نامعتبر به `SERVER_ERROR` تبدیل می‌شود.

فقط پاسخ `OK` با TTL بزرگ‌تر از صفر در کش ذخیره می‌شود. TTL باقی‌مانده با گذشت زمان کم می‌شود و وقتی کمتر از یک ثانیه باشد، ورودی منقضی است. `NOT_FOUND`، `SERVER_ERROR` و پاسخ فهرست‌ها کش نمی‌شوند. اگر کش خاموش باشد، نه خوانده می‌شود و نه نوشته.

## ۷) تست‌ها

اجرای تست‌های واحد و یکپارچه:

```powershell
python -m pytest -q
```

تولید مجدد transcript آزمون‌های پذیرش T1 تا T13:

```powershell
python tests/run_acceptance.py
```

خروجی در `test_results.txt` ذخیره می‌شود. در زمان آماده‌سازی این نسخه، مجموعه تست خودکار با نتیجه `31 passed` اجرا شده است. تست‌ها از UDP واقعی روی localhost برای Upstream mock استفاده می‌کنند. تست B6 با پاسخ‌های DNS wire-format کنترل‌شده انجام می‌شود تا استخراج A/TTL و NXDOMAIN بدون وابستگی به اینترنت قابل تکرار باشد؛ تست زنده با DNS عمومی نیازمند دسترسی بیرونی UDP/53 است.

## ۸) قابلیت‌های امتیازی پیاده‌سازی‌شده

- B1: آمار Total، AD_BLOCK، SANCTION، CACHE، UPSTREAM و ERRORS
- B2: reload بدون راه‌اندازی مجدد
- B3: نمایش کش زنده و TTL باقی‌مانده
- B4: ثبت هر درخواست دامنه در `log.txt` با قالب شش‌ستونی جداشده با `|`
- B5: ظرفیت اختیاری کش با FIFO
- B6: پرس‌وجوی واقعی DNS نوع A از DNS عمومی و نگهداری TTL واقعی

## ۹) ساختار پروژه

```text
DNS-Proxy/
├── main.py                 # CLI
├── upstream_mock.py        # UDP text Upstream simulator
├── run_both.py             # CLI + Web with one shared engine
├── config.txt
├── ad_list.txt
├── sanction_list.txt
├── log.txt                 # created on first domain request
├── test_results.txt        # generated acceptance transcript
├── dnsproxy/               # shared Python core
├── web/                    # local browser interface
└── tests/                  # unit, integration and acceptance tests
```

## ۱۰) محدوده و محدودیت‌ها

- رابط وب افزونه درخواستی پروژه است؛ بخش اجباری کنسول مستقل باقی مانده است.
- بخش اجباری فقط از IPv4 و رکورد A در B6 استفاده می‌کند؛ IPv6 و رکوردهای دیگر DNS در محدوده این فاز نیستند.
- در بخش اصلی، Upstream شبیه‌ساز متن‌محور است؛ پیام باینری DNS فقط در B6 به‌کار می‌رود.
- برنامه یک DNS Proxy آموزشی است، نه تونل TCP/HTTPS و نه خودِ سرور واسط شبکه.
- برای تحویل دانشگاهی، اعضای گروه باید منطق برنامه و سهم خود را در جلسه تحویل توضیح دهند؛ این مورد با تست خودکار قابل جایگزینی نیست.
